3.1 Herramienta para crear y administrar la estructura de Base de Datos Relacionales

Definición

Las herramientas gráficas de administración son aplicaciones (normalmente con interfaz gráfica) que permiten a un DBA crear y modificar tablas, relaciones, índices y demás objetos de una base de datos sin escribir DDL a mano. Por dentro, cada acción que se hace con el ratón termina generando exactamente el mismo CREATE/ALTER que se estudió en la Unidad I, tema 1.5 — esto es justamente lo que exige la Regla 5 de Codd (sublenguaje de datos comprensivo, ver Unidad I, tema 1.2).

Tabla 1: Herramientas de administración de estructura por motor

MotorHerramienta oficial
MySQL / MariaDBMySQL Workbench
Microsoft SQL ServerSQL Server Management Studio (SSMS)
PostgreSQLpgAdmin
OracleOracle SQL Developer

Ejemplo

Crear la tabla Proveedores desde el diseñador visual de una herramienta como MySQL Workbench normalmente implica:

  1. Clic derecho sobre el esquema → "Create Table".
  2. Escribir el nombre Proveedores y agregar columnas desde una cuadrícula (nombre, tipo de dato, si es PK, NN, etc.).
  3. Definir la relación con Productos arrastrando una clave foránea en el diagrama entidad-relación (EER).
  4. Dar clic en "Apply": la herramienta genera y muestra el script SQL antes de ejecutarlo.

El script generado por la herramienta es exactamente equivalente a escribirlo a mano:

CREATE TABLE Proveedores (
    id_proveedor INT PRIMARY KEY AUTO_INCREMENT,
    razon_social VARCHAR(120) NOT NULL,
    telefono     VARCHAR(15)
);

ALTER TABLE Productos
    ADD COLUMN id_proveedor INT,
    ADD FOREIGN KEY (id_proveedor) REFERENCES Proveedores(id_proveedor);

Planes de ejecución

Además de crear objetos, estas herramientas permiten pedirle al optimizador (Unidad I, tema 1.3) que muestre el plan de ejecución de una consulta: la secuencia de pasos (qué índices usa, en qué orden combina las tablas) que eligió para resolverla. Leer un plan de ejecución es la forma más directa de saber por qué una consulta es lenta.

Ejemplo — Plan de ejecución

-- Ver el plan de ejecución sin ejecutar la consulta (MySQL/PostgreSQL)
EXPLAIN SELECT nombre FROM Productos WHERE categoria = 'Zapatos';

-- PostgreSQL: además de mostrar el plan, ejecuta la consulta y mide tiempos reales
EXPLAIN ANALYZE SELECT nombre FROM Productos WHERE categoria = 'Zapatos';

Si el plan muestra un "Seq Scan" (recorrido secuencial completo) sobre una tabla grande en lugar de un "Index Scan", probablemente falte un índice sobre esa columna (ver índices clusterizados/no clusterizados en Unidad I, tema 1.4).

3.2 Herramienta para crear y administrar usuarios y privilegios

Definición

Estas herramientas permiten crear cuentas de usuario, agruparlas en roles y asignarles privilegios (permisos) de forma visual, sin perder el control fino que ya se vio con GRANT/REVOKE en la Unidad II, tema 2.2. Los privilegios pueden otorgarse en distintos niveles de granularidad.

Tabla 2: Niveles de privilegio

NivelEjemplo de alcanceInstrucción típica
ServidorCrear bases de datos, crear otros logins.CREATE LOGIN
Base de datosConectarse a una base de datos específica.CREATE USER, GRANT CONNECT
ObjetoLeer o modificar una tabla o vista concreta.GRANT SELECT ON tabla

Ejemplo

Desde la herramienta gráfica, crear un usuario de solo lectura implica: Seguridad → Logins → Nuevo login, asignarle un rol de base de datos existente o crear uno. El resultado equivale a:

CREATE ROLE solo_lectura;
GRANT SELECT ON Farmacia.* TO solo_lectura;

CREATE USER 'pasante'@'localhost' IDENTIFIED BY 'ClaveSegura123';
GRANT solo_lectura TO 'pasante'@'localhost';

3.3 Herramienta para crear y administrar respaldos, dispositivos de recuperación y archivos bitácora

Definición

Estas herramientas incluyen asistentes ("wizards") para programar los respaldos vistos en la Unidad II, tema 2.5, definir dispositivos de respaldo (la ubicación física donde se guardan) y administrar el archivo bitácora: el registro de transacciones que el motor usa para recuperación, y cuyo nombre técnico cambia según el motor.

Tabla 3: Archivo de bitácora por motor

MotorNombre técnico del archivo bitácora
Microsoft SQL ServerTransaction Log (archivo .ldf)
MySQL / MariaDBBinary Log (binlog)
PostgreSQLWrite-Ahead Log (WAL)
OracleRedo Log

Ejemplo

En SSMS, el asistente de mantenimiento ("Maintenance Plan Wizard") permite programar visualmente un respaldo completo semanal y uno diferencial diario, escogiendo el dispositivo de respaldo (una carpeta local o de red). Por dentro, genera un trabajo programado equivalente a:

BACKUP DATABASE Farmacia
TO DISK = 'D:\Respaldos\Farmacia_completo.bak'
WITH INIT, NAME = 'Respaldo completo semanal';

3.4 Herramientas para administrar y configurar

Definición

Conforme una organización crece, administrar un SMBDR deja de ser administrar un solo servidor. Este tema agrupa las herramientas para configurar los módulos del motor, coordinar varios servidores mediante replicación, y monitorear el ambiente completo.

3.4.1 Módulos de los Sistemas Manejadores de Bases de Datos Relacionales

La mayoría de los SMBDR modernos se organizan en módulos instalables por separado, cada uno con una función administrativa específica: por ejemplo, un agente de tareas programadas (SQL Server Agent en SQL Server, pgAgent en PostgreSQL), un módulo de análisis de rendimiento (Profiler / Extended Events), o módulos de integración y reportes (SQL Server Integration/Reporting Services). Instalar solo los módulos necesarios reduce el consumo de recursos del servidor.

3.4.2 Replicación y múltiples servidores

La replicación mantiene una copia sincronizada de la base de datos en otro servidor. El esquema más común es maestro-esclavo (master-slave): todas las escrituras se hacen en el servidor primario (maestro), y se propagan automáticamente —vía el archivo bitácora— a uno o más servidores réplica (esclavos), que normalmente atienden solo lecturas. Esto mejora la disponibilidad y distribuye la carga de consultas.

Tabla 4: Tipos de replicación

TipoDescripción
SíncronaEl maestro espera la confirmación de la réplica antes de confirmar la transacción; máxima consistencia, mayor latencia.
AsíncronaEl maestro confirma sin esperar a la réplica; menor latencia, con un pequeño riesgo de perder los cambios más recientes si el maestro falla.
Transaccional (SQL Server)Replica cada transacción confirmada casi en tiempo real.
Instantánea (snapshot) (SQL Server)Replica una "foto" completa de los datos en intervalos programados, no cambio a cambio.
De fusión (merge) (SQL Server)Permite que tanto el maestro como las réplicas hagan cambios, y los combina; útil en escenarios desconectados.

3.4.3 Múltiples servidores

Además de la replicación, las herramientas de administración permiten agrupar varios servidores bajo una sola consola ("grupos de servidores" en SSMS, "Server Groups" en MySQL Workbench o pgAdmin), de modo que el DBA pueda ejecutar la misma tarea de mantenimiento o consulta contra todos ellos a la vez, en lugar de conectarse uno por uno.

3.4.4 Monitoreo del ambiente del SMBDR

El monitoreo consiste en vigilar en tiempo real el estado del servidor para detectar problemas antes de que afecten a los usuarios:

Tabla 5: Métricas comunes de monitoreo

MétricaQué revelaHerramienta de ejemplo
Uso de CPU y memoriaSi el servidor está saturado.Activity Monitor (SSMS)
Conexiones activasCuántos usuarios/procesos están conectados.pg_stat_activity (PostgreSQL)
Bloqueos activosPosibles cuellos de botella de concurrencia (ver Unidad II, tema 2.3).Vistas de administración dinámica (DMV)
Consultas lentasQué instrucciones SQL conviene optimizar.Performance Schema (MySQL)

3.4.5 Particionamiento y motores de almacenamiento

Dos decisiones de diseño físico que un DBA suele ajustar cuando una tabla crece mucho son el motor de almacenamiento (en motores que lo permiten, como MySQL/MariaDB) y el particionamiento. Un motor de almacenamiento define cómo se guardan y bloquean físicamente las filas de una tabla: por ejemplo, en MySQL, InnoDB soporta transacciones e integridad referencial (es el motor recomendado casi siempre), mientras que MyISAM es más simple y en ciertos escenarios de solo lectura puede ser más rápido, pero no soporta FOREIGN KEY ni transacciones. El particionamiento, por su parte, divide físicamente una sola tabla lógica en varios segmentos de almacenamiento, sin que el usuario tenga que cambiar sus consultas.

Tabla 6: Tipos de particionamiento

TipoCómo divide las filasEjemplo de uso
RANGEPor rangos de valores de una columna.Ventas particionadas por año (2024, 2025, 2026…).
LISTPor una lista explícita de valores permitidos.Sucursales particionadas por región (Norte, Centro, Sur).
HASHPor una función hash aplicada a una columna, para repartir las filas de forma uniforme.Distribuir clientes entre varias particiones sin un criterio de negocio evidente.

Ejemplo — Particionamiento por rango

-- MySQL: la tabla Ventas queda dividida físicamente en 3 particiones por año,
-- pero para quien la consulta sigue siendo una sola tabla lógica
CREATE TABLE Ventas (
    id_venta INT NOT NULL,
    fecha    DATE NOT NULL,
    total    DECIMAL(8,2) NOT NULL
)
PARTITION BY RANGE (YEAR(fecha)) (
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION p2026 VALUES LESS THAN (2027)
);

Una consulta como SELECT * FROM Ventas WHERE fecha BETWEEN '2026-01-01' AND '2026-06-30' solo necesita revisar la partición p2026 (partition pruning), en lugar de recorrer los tres años completos.

3.5 Utilerías de mantenimiento y asistentes de tareas administrativas

Definición

Son programas y asistentes que automatizan tareas rutinarias de mantenimiento: verificar la integridad física de los archivos, reorganizar índices fragmentados, actualizar estadísticas que usa el optimizador de consultas (ver Unidad I, tema 1.3), y programar todo esto para que se ejecute solo, sin intervención manual.

Tabla 7: Utilerías de mantenimiento por motor

UtileríaMotorPropósito
DBCC CHECKDBSQL ServerVerifica la integridad física y lógica de la base de datos.
VACUUM / ANALYZEPostgreSQLRecupera espacio de filas eliminadas y actualiza estadísticas.
OPTIMIZE TABLEMySQL / MariaDBReorganiza y desfragmenta una tabla.
SQL Server Agent / pgAgent / cronTodos (equivalentes)Programa tareas de mantenimiento para que corran automáticamente.

Ejemplo

-- PostgreSQL: recuperar espacio y refrescar estadísticas tras muchos DELETE
VACUUM ANALYZE Ventas;

-- MySQL: desfragmentar una tabla con mucha rotación de filas
OPTIMIZE TABLE Ventas;

-- SQL Server: verificar la integridad de toda la base de datos
DBCC CHECKDB ('Farmacia');

Estas instrucciones normalmente no se ejecutan a mano cada vez: se programan dentro de un plan de mantenimiento (asistente gráfico) para que corran, por ejemplo, cada domingo de madrugada.

Apéndice: Repaso de diagrama Entidad-Relación y normalización

El Proyecto Integrador de esta unidad pide un diagrama entidad-relación propio y un diseño normalizado hasta la 3FN. Estos temas se cubren a fondo en la materia antecedente Construcción de Bases de Datos; aquí va solo un repaso rápido para tenerlos frescos antes de empezar el proyecto.

Diagrama Entidad-Relación (E-R)

Un diagrama E-R representa, antes de construir las tablas, qué información existe y cómo se relaciona: una entidad es un objeto del negocio (se convierte en tabla), un atributo es una de sus propiedades (columna), y una relación conecta dos entidades indicando su cardinalidad: 1:1, 1:N o N:M. Una relación N:M no puede implementarse directamente como clave foránea; se resuelve creando una tabla intermedia que la convierte en dos relaciones 1:N.

Figura 2: Diagrama propio — ejemplo de notación E-R con cardinalidades 1:N; úsalo solo como referencia de notación, tu proyecto debe modelar un negocio distinto.

Normalización

La normalización es el proceso de organizar las tablas para reducir la redundancia y evitar anomalías al insertar, actualizar o eliminar datos, aplicando reglas progresivas llamadas formas normales.

Tabla 8: Formas normales básicas

FormaRegla
1FN (Primera Forma Normal)Cada columna contiene un solo valor atómico (sin listas ni grupos repetidos), y existe una clave primaria.
2FN (Segunda Forma Normal)Cumple 1FN y, si la clave primaria es compuesta, todo atributo no clave depende de la clave completa (no de una parte de ella).
3FN (Tercera Forma Normal)Cumple 2FN y ningún atributo no clave depende de otro atributo no clave (no hay dependencias transitivas).

Ejemplo — Antes y después de normalizar

La tabla Ventas(id_venta, id_producto, nombre_producto, precio_producto, cantidad) viola la 3FN: nombre_producto y precio_producto no dependen de id_venta, sino de id_producto (dependencia transitiva). Se normaliza separándola en dos tablas:

-- Antes (sin normalizar): datos del producto repetidos en cada venta
Ventas(id_venta, id_producto, nombre_producto, precio_producto, cantidad)

-- Después (normalizado a 3FN)
Ventas(id_venta, id_producto (FK), cantidad)
Productos(id_producto (PK), nombre_producto, precio_producto)

Así, si cambia el precio de un producto, se actualiza en un solo lugar (Productos) en vez de en cada venta donde aparecía repetido. Estos son los mismos criterios que se piden aplicar en las Fases 1 y 2 del Proyecto Integrador: tu diagrama E-R debe usar una notación equivalente a la de la Figura 2, y tu diseño relacional debe llegar, como mínimo, hasta la 3FN.
