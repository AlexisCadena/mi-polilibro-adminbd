3.1 Herramienta para crear y administrar la estructura de Base de Datos Relacionales

La analogía del coche automático

Las herramientas con ventanas y botones son como manejar un coche automático. Haces clic para crear una tabla, arrastras para relacionarla, marcas una casilla para ponerle un índice y ya, no escribes DDL a mano.

Pero por debajo el motor hace lo de siempre. Cada clic termina escribiendo el mismo CREATE o el mismo ALTER que viste en la Unidad I, tema 1.5. De hecho, que todo se pueda hacer con un solo lenguaje por debajo es justo lo que pide la Regla 5 de Codd, que viste en la Unidad I, tema 1.2.

Tabla 1 — Herramienta de cada motor para armar la estructura

MotorHerramienta oficial
MySQL / MariaDBMySQL Workbench
Microsoft SQL ServerSQL Server Management Studio (SSMS)
PostgreSQLpgAdmin
OracleOracle SQL Developer

Ejemplo

Crear la tabla Proveedores desde el diseñador visual de una herramienta como MySQL Workbench casi siempre es así

  1. Clic derecho sobre el esquema → "Create Table".
  2. Escribir el nombre Proveedores y agregar columnas desde una cuadrícula (nombre, tipo de dato, si es PK, NN, etc.).
  3. Definir la relación con Productos arrastrando una clave foránea en el diagrama entidad-relación (EER).
  4. Dar clic en "Apply" y la herramienta genera y muestra el script SQL antes de ejecutarlo.

El script que arma la herramienta es igualito a escribirlo a mano

CREATE TABLE Proveedores (
    id_proveedor INT PRIMARY KEY AUTO_INCREMENT,
    razon_social VARCHAR(120) NOT NULL,
    telefono     VARCHAR(15)
);

ALTER TABLE Productos
    ADD COLUMN id_proveedor INT,
    ADD FOREIGN KEY (id_proveedor) REFERENCES Proveedores(id_proveedor);

Cómo saber por qué una consulta va lenta

Aparte de crear objetos, estas herramientas te dejan pedirle al optimizador de la Unidad I, tema 1.3 que te enseñe su plan de ejecución. Ese plan es la lista de pasos que va a seguir para resolver una consulta, como qué índices usa y en qué orden junta las tablas. Leer ese plan es la forma más directa de entender por qué una consulta va lenta.

Ejemplo — Plan de ejecución

-- Ver el plan de ejecución sin ejecutar la consulta (MySQL/PostgreSQL)
EXPLAIN SELECT nombre FROM Productos WHERE categoria = 'Zapatos';

-- PostgreSQL: además de mostrar el plan, ejecuta la consulta y mide tiempos reales
EXPLAIN ANALYZE SELECT nombre FROM Productos WHERE categoria = 'Zapatos';

Si el plan dice "Seq Scan", que quiere decir que va a recorrer toda la tabla de arriba a abajo, y la tabla es grande, seguramente falta un índice en esa columna, como viste en la Unidad I, tema 1.4.

3.2 Herramienta para crear y administrar usuarios y privilegios

La analogía de la oficina de credenciales

Estas herramientas son como la oficina que hace las credenciales de la escuela. Das de alta a una persona, le entregas su credencial, que sería la cuenta de usuario, y le marcas a qué puertas abre.

Para no hacer el trámite uno por uno, se arman roles, que son juegos de permisos ya listos, como "maestro", "prefecto" o "cajero", y se los cuelgas a la credencial. Todo esto es el mismo GRANT y REVOKE de la Unidad II, tema 2.2, pero a golpe de clic. Y se puede dar con más o menos detalle, sobre toda la base, sobre una tabla o sobre una sola columna.

Tabla 2 — Niveles de permiso

NivelEjemplo de alcanceInstrucción típica
ServidorCrear bases de datos, crear otros logins.CREATE LOGIN
Base de datosConectarse a una base de datos específica.CREATE USER, GRANT CONNECT
ObjetoLeer o modificar una tabla o vista concreta.GRANT SELECT ON tabla

Ejemplo

Desde la herramienta gráfica, para crear un usuario de solo lectura vas a Seguridad, luego Logins, luego Nuevo login, y le asignas un rol que ya exista o creas uno. El resultado es el mismo que esto

CREATE ROLE solo_lectura;
GRANT SELECT ON Farmacia.* TO solo_lectura;

CREATE USER 'pasante'@'localhost' IDENTIFIED BY 'ClaveSegura123';
GRANT solo_lectura TO 'pasante'@'localhost';

3.3 Herramienta para crear y administrar respaldos, dispositivos de recuperación y archivos bitácora

La analogía del asistente que programa las fotocopias

Aquí las herramientas traen asistentes que te llevan de la mano para programar los respaldos de la Unidad II, tema 2.5. Tú les dices cada cuándo se hacen, de qué tipo y a dónde van.

El "a dónde van" es el dispositivo de respaldo, o sea el lugar donde se guardan las copias, como un disco, una cinta o una carpeta en la red. Y el archivo bitácora es el diario del motor. Ahí queda anotado cada cambio, y es lo que se usa para recuperar la base cuando algo falla. Su nombre técnico cambia de un manejador a otro.

Tabla 3 — Cómo se llama el archivo bitácora en cada motor

MotorNombre técnico del archivo bitácora
Microsoft SQL ServerTransaction Log (archivo .ldf)
MySQL / MariaDBBinary Log (binlog)
PostgreSQLWrite-Ahead Log (WAL)
OracleRedo Log

Ejemplo

En SSMS, el asistente de mantenimiento te deja programar con clics un respaldo completo cada semana y uno diferencial cada día, y elegir el dispositivo de respaldo, que puede ser una carpeta local o de red. Por dentro arma una tarea programada como esta

BACKUP DATABASE Farmacia
TO DISK = 'D:\Respaldos\Farmacia_completo.bak'
WITH INIT, NAME = 'Respaldo completo semanal';

3.4 Herramientas para administrar y configurar

La analogía de la tiendita que se vuelve cadena

Cuando la organización crece, administrar un SMBDR ya no es cuidar un solo servidor, igual que llevar una cadena de tiendas no es lo mismo que atender una tiendita.

Este tema junta las herramientas para tres cosas. Configurar las partes de adentro del motor, como acomodar cada área de la tienda. Coordinar varios servidores con replicación, para que todas las sucursales tengan el mismo inventario al día. Y vigilar todo el ambiente, como las cámaras que te avisan si algo se está saliendo de control.

3.4.1 Módulos de los Sistemas Manejadores de Bases de Datos Relacionales

Casi todos los SMBDR de hoy vienen en piezas que se instalan por separado, y cada pieza hace una tarea distinta. Por ejemplo, una pieza que corre tareas a cierta hora, otra que mide el rendimiento y otra que arma reportes. Instalar solo las piezas que de verdad se van a usar hace que el servidor gaste menos recursos.

3.4.2 Replicación y múltiples servidores

La replicación mantiene una copia al día de la base de datos en otro servidor. Lo más común es el modo maestro y réplica. Todas las escrituras se hacen en el servidor principal, el maestro, y de ahí se copian solas, usando el archivo bitácora, a uno o varios servidores réplica que casi siempre solo atienden lecturas. Esto ayuda a que el sistema no se caiga y reparte el trabajo de las consultas.

Tabla 4 — Tipos de replicación

TipoDescripción
SíncronaEl maestro espera a que la réplica confirme antes de dar por buena la operación. Es lo más seguro pero va más lento.
AsíncronaEl maestro confirma sin esperar a la réplica. Va más rápido, con un riesgo chico de perder los últimos cambios si el maestro se cae.
Transaccional (SQL Server)Copia cada cambio confirmado casi al instante.
Instantánea (SQL Server)Copia una "foto" completa de los datos cada cierto tiempo, no cambio por cambio.
De fusión (SQL Server)Deja que tanto el maestro como las réplicas hagan cambios y luego los junta. Sirve cuando los equipos pasan ratos sin conexión.

3.4.3 Múltiples servidores

Aparte de la replicación, las herramientas dejan juntar varios servidores en una sola ventana, en lo que se llaman grupos de servidores, para que el DBA pueda correr la misma tarea o la misma consulta en todos a la vez, en lugar de entrar uno por uno.

3.4.4 Monitoreo del ambiente del SMBDR

Monitorear es vigilar en vivo cómo va el servidor, para cachar los problemas antes de que los sientan los usuarios

3.4.5 Particionamiento y motores de almacenamiento

Cuando una tabla crece mucho, el DBA suele tocar dos cosas de cómo se guarda por dentro. Una es el motor de almacenamiento, que decide cómo se guardan y se bloquean las filas. En MySQL, InnoDB entiende de transacciones y de relaciones entre tablas, y es el que se recomienda casi siempre. MyISAM es más simple y en algunos casos de solo lectura va más rápido, pero no entiende de FOREIGN KEY ni de transacciones. La otra cosa es el particionamiento, que parte una sola tabla en varios pedazos guardados aparte, y el usuario ni se entera porque sigue consultando igual.

Tabla 6 — Formas de partir una tabla

TipoCómo divide las filasEjemplo de uso
RANGEPor tramos de valores de una columna.Ventas partidas por año (2024, 2025, 2026…).
LISTPor una lista de valores permitidos.Sucursales partidas por región (Norte, Centro, Sur).
HASHCon una fórmula que reparte las filas de forma pareja.Repartir clientes entre varios pedazos sin un criterio claro de negocio.

Ejemplo — Particionamiento por rango

-- MySQL: la tabla Ventas queda dividida físicamente en 3 particiones por año,
-- pero para quien la consulta sigue siendo una sola tabla lógica
CREATE TABLE Ventas (
    id_venta INT NOT NULL,
    fecha    DATE NOT NULL,
    total    DECIMAL(8,2) NOT NULL
)
PARTITION BY RANGE (YEAR(fecha)) (
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION p2026 VALUES LESS THAN (2027)
);

Una consulta como SELECT * FROM Ventas WHERE fecha BETWEEN '2026-01-01' AND '2026-06-30' solo tiene que revisar el pedazo p2026, en lugar de recorrer los tres años completos.

3.5 Utilerías de mantenimiento y asistentes de tareas administrativas

La analogía del equipo de mantenimiento nocturno

Son programas y asistentes que hacen la limpieza pesada mientras nadie ve, como el equipo que entra de noche a darle servicio al edificio.

Lo que suelen hacer es revisar que los archivos no estén dañados, reacomodar los índices que quedaron desordenados de tanto uso, actualizar las estadísticas que el optimizador necesita para elegir buenos caminos, como viste en la Unidad I, tema 1.3, y lo más importante, dejar todo eso programado para que corra solo sin que el DBA tenga que acordarse.

Tabla 7 — Utilerías de mantenimiento de cada motor

UtileríaMotorPropósito
DBCC CHECKDBSQL ServerRevisa que la base de datos no tenga daños por dentro.
VACUUM / ANALYZEPostgreSQLRecupera el espacio de las filas borradas y refresca las estadísticas.
OPTIMIZE TABLEMySQL / MariaDBReacomoda y compacta una tabla.
SQL Server Agent / pgAgent / cronTodos (equivalentes)Programa tareas de mantenimiento para que corran automáticamente.

Ejemplo

-- PostgreSQL: recuperar espacio y refrescar estadísticas tras muchos DELETE
VACUUM ANALYZE Ventas;

-- MySQL: desfragmentar una tabla con mucha rotación de filas
OPTIMIZE TABLE Ventas;

-- SQL Server: verificar la integridad de toda la base de datos
DBCC CHECKDB ('Farmacia');

Estas instrucciones casi nunca se corren a mano. Se meten en un plan de mantenimiento, con su asistente de ventanas, para que corran solas, por ejemplo cada domingo de madrugada.

Apéndice. Repaso de diagrama Entidad-Relación y normalización

El Proyecto Integrador de esta unidad pide un diagrama entidad-relación propio y un diseño normalizado hasta la 3FN. Estos temas se ven a fondo en la materia anterior, Construcción de Bases de Datos. Aquí va solo un repaso rápido para tenerlos frescos antes de empezar el proyecto.

Diagrama Entidad-Relación (E-R)

Un diagrama E-R muestra, antes de armar las tablas, qué información hay y cómo se conecta. Una entidad es una cosa del negocio y termina siendo una tabla. Un atributo es una de sus características y termina siendo una columna. Y una relación une dos entidades y dice cuántos van con cuántos, o sea uno a uno, uno a muchos o muchos a muchos. Una relación de muchos a muchos no se puede poner directo con una llave foránea. Se resuelve metiendo una tabla en medio que la parte en dos relaciones de uno a muchos.

Figura 2. Diagrama propio. Un ejemplo de cómo se dibuja un E-R con relaciones de uno a muchos. Úsalo solo como muestra del dibujo, tu proyecto debe ser de otro negocio.

Normalización

Normalizar es acomodar las tablas para que no haya datos repetidos y para que no se hagan líos al meter, cambiar o borrar información. Se hace siguiendo unas reglas que van una tras otra y se llaman formas normales.

Tabla 8 — Las tres primeras formas normales

FormaRegla
1FN (Primera Forma Normal)Cada celda guarda un solo valor, sin listas ni grupos repetidos, y la tabla tiene llave primaria.
2FN (Segunda Forma Normal)Cumple la 1FN y, si la llave primaria está hecha de varias columnas, cada dato que no es llave depende de la llave completa y no de un pedazo de ella.
3FN (Tercera Forma Normal)Cumple la 2FN y ningún dato que no es llave depende de otro dato que tampoco es llave.

Ejemplo — Antes y después de normalizar

La tabla Ventas(id_venta, id_producto, nombre_producto, precio_producto, cantidad) rompe la 3FN, porque nombre_producto y precio_producto no dependen de id_venta sino de id_producto. Se arregla partiéndola en dos tablas

-- Antes (sin normalizar): datos del producto repetidos en cada venta
Ventas(id_venta, id_producto, nombre_producto, precio_producto, cantidad)

-- Después (normalizado a 3FN)
Ventas(id_venta, id_producto (FK), cantidad)
Productos(id_producto (PK), nombre_producto, precio_producto)

Así, si cambia el precio de un producto, lo cambias en un solo lugar, en Productos, en vez de en cada venta donde estaba repetido. Estos son los mismos criterios que se piden en las Fases 1 y 2 del Proyecto Integrador. Tu diagrama E-R debe usar un dibujo parecido al de la Figura 2, y tu diseño debe llegar por lo menos hasta la 3FN.
