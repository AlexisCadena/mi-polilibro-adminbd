2.1 Consultas simples y multitabla

Definición

Una consulta (query) es una instrucción SQL, casi siempre basada en SELECT, que solicita al SMBDR un subconjunto de información. Una consulta simple obtiene datos de una sola tabla. Una consulta multitabla combina información de dos o más tablas relacionadas mediante una operación JOIN, aprovechando las claves foráneas definidas en el modelo relacional (ver Unidad I, tema 1.2).

La anatomía general de una consulta simple es:

SELECT columna1, columna2        -- qué columnas mostrar
FROM tabla                        -- de qué tabla
WHERE condicion                   -- qué filas filtrar
GROUP BY columna                  -- cómo agrupar (opcional)
HAVING condicion_de_grupo         -- filtro sobre los grupos (opcional)
ORDER BY columna ASC|DESC;        -- cómo ordenar el resultado

Cuando la información que se necesita vive en más de una tabla, se recurre a un JOIN. Existen cuatro tipos principales:

Tabla 1: Tipos de JOIN

TipoQué devuelve
INNER JOINSolo las filas que tienen coincidencia en ambas tablas.
LEFT JOINTodas las filas de la tabla izquierda, tengan o no coincidencia en la derecha (rellena con NULL si no hay).
RIGHT JOINTodas las filas de la tabla derecha, tengan o no coincidencia en la izquierda.
FULL JOINTodas las filas de ambas tablas, coincidan o no (unión de LEFT y RIGHT).

Figura 1: Diagrama propio — los cuatro tipos de JOIN representados como diagramas de Venn (la zona guinda es lo que devuelve cada uno).

Ejemplo

Con las tablas Alumnos(id_alumno, nombre) e Inscripciones(id_inscripcion, id_alumno, materia):

-- Consulta simple: solo alumnos
SELECT nombre FROM Alumnos;

-- Consulta multitabla: alumnos con su materia inscrita
SELECT A.nombre, I.materia
FROM Alumnos A
INNER JOIN Inscripciones I ON A.id_alumno = I.id_alumno;

-- Alumnos aunque todavía no se hayan inscrito a nada
SELECT A.nombre, I.materia
FROM Alumnos A
LEFT JOIN Inscripciones I ON A.id_alumno = I.id_alumno;

El LEFT JOIN es útil precisamente para detectar alumnos sin inscripción: en esas filas, I.materia aparecerá como NULL.

Funciones de agregación

Las funciones de agregación calculan un valor resumen a partir de un conjunto de filas. Se usan solas (sobre toda la tabla) o combinadas con GROUP BY (un resultado por cada grupo) y, opcionalmente, HAVING (para filtrar esos grupos ya calculados, a diferencia de WHERE, que filtra filas individuales antes de agrupar).

Tabla 2: Funciones de agregación

FunciónQué calcula
COUNTNúmero de filas (o de valores no nulos de una columna).
SUMSuma de los valores de una columna numérica.
AVGPromedio de los valores de una columna numérica.
MAXValor máximo de la columna.
MINValor mínimo de la columna.

Ejemplo — Funciones de agregación

-- Total de ventas registradas
SELECT COUNT(*) AS total_ventas FROM Ventas;

-- Ingreso total y promedio por producto vendido
SELECT id_producto, SUM(total) AS ingreso_total, AVG(total) AS venta_promedio
FROM Ventas
GROUP BY id_producto;

-- Solo los productos con más de 5 ventas registradas
SELECT id_producto, COUNT(*) AS num_ventas
FROM Ventas
GROUP BY id_producto
HAVING COUNT(*) > 5;

GROUP BY agrupa las filas que comparten el mismo valor en id_producto antes de aplicar la función de agregación; HAVING filtra esos grupos ya calculados.

Subconsultas

Una subconsulta (subquery) es una instrucción SELECT anidada dentro de otra consulta, normalmente dentro de WHERE, FROM o SELECT. Es no correlacionada cuando no depende de la consulta externa (se ejecuta una sola vez); es correlacionada cuando hace referencia a una columna de la consulta externa (se vuelve a evaluar por cada fila).

Ejemplo — Subconsultas

-- No correlacionada: productos más caros que el precio promedio
SELECT nombre, precio
FROM Productos
WHERE precio > (SELECT AVG(precio) FROM Productos);

-- Correlacionada: clientes que tienen al menos una venta registrada
SELECT nombre
FROM Clientes C
WHERE EXISTS (
    SELECT 1 FROM Ventas V WHERE V.id_cliente = C.id_cliente
);

Operadores de conjunto

Los operadores de conjunto combinan el resultado de dos consultas SELECT que tengan el mismo número de columnas y tipos compatibles, tratándolos como conjuntos matemáticos.

Tabla 3: Operadores de conjunto

OperadorQué devuelve
UNIONFilas que aparecen en cualquiera de las dos consultas, sin duplicados (UNION ALL sí los conserva).
INTERSECTSolo las filas que aparecen en ambas consultas.
EXCEPT (o MINUS en Oracle)Filas de la primera consulta que no aparecen en la segunda.

Ejemplo — Operadores de conjunto

-- Nombres de personas que son clientes o empleados (sin duplicados)
SELECT nombre FROM Clientes
UNION
SELECT nombre FROM Empleados;

-- Productos que se han vendido Y tienen stock por debajo del mínimo
SELECT id_producto FROM Ventas
INTERSECT
SELECT id_producto FROM Productos WHERE stock < stock_minimo;

2.2 Administración de la seguridad e integridad de la información en un SMBDR

Definición

La seguridad regula quién puede acceder al SMBDR y qué puede hacer (autenticación y autorización mediante GRANT/REVOKE, vistas en Unidad I, tema 1.5). La integridad garantiza que los datos almacenados sean correctos y consistentes, mediante restricciones (constraints) definidas sobre las propias tablas.

Las restricciones de integridad más comunes son:

Tabla 4: Restricciones de integridad

RestricciónQué garantiza
PRIMARY KEYIntegridad de entidad: cada fila es única e identificable.
FOREIGN KEYIntegridad referencial: el valor debe existir en la tabla referenciada.
NOT NULLEl campo no puede quedar vacío.
UNIQUENo se permiten valores repetidos en esa columna.
CHECKEl valor debe cumplir una condición lógica (por ejemplo, edad >= 0).
DEFAULTAsigna un valor automático cuando no se especifica ninguno.

Ejemplo

Restricciones de integridad al crear una tabla, y administración de la seguridad mediante un rol:

CREATE TABLE Empleados (
    id_empleado  INT PRIMARY KEY AUTO_INCREMENT,
    nombre       VARCHAR(100) NOT NULL,
    correo       VARCHAR(120) UNIQUE,
    salario      DECIMAL(10,2) CHECK (salario > 0),
    id_depto     INT,
    activo       BOOLEAN DEFAULT TRUE,
    FOREIGN KEY (id_depto) REFERENCES Departamentos(id_depto)
);

-- Seguridad: un rol de solo lectura para auditoría
CREATE ROLE auditor_rrhh;
GRANT SELECT ON Empleados TO auditor_rrhh;
GRANT auditor_rrhh TO 'usuario_auditoria';

3. Dos empleados quedaron registrados con el mismo correo electrónico.

2.3 Control de concurrencia y técnicas de bloqueo

Definición

El control de concurrencia es el conjunto de mecanismos que permite que varias transacciones se ejecuten al mismo tiempo sin que unas interfieran con los datos de otras. La técnica más común es el bloqueo (locking): antes de leer o modificar un dato, una transacción solicita un candado sobre él.

Sin control de concurrencia pueden ocurrir varias anomalías:

  • Pérdida de actualización (lost update): dos transacciones sobrescriben el cambio de la otra.
  • Lectura sucia (dirty read): una transacción lee datos que otra modificó pero aún no confirmó (COMMIT).
  • Lectura no repetible (non-repeatable read): al leer el mismo dato dos veces dentro de la misma transacción, se obtienen valores distintos.
  • Lectura fantasma (phantom read): una consulta repetida devuelve filas nuevas que otra transacción insertó de por medio.

Existen dos tipos básicos de bloqueo:

Tabla 5: Compatibilidad de bloqueos

Compartido (S) de otra transacciónExclusivo (X) de otra transacción
Compartido (S) — para lecturaCompatible: ambas pueden leer a la vez.Incompatible: debe esperar.
Exclusivo (X) — para escrituraIncompatible: debe esperar.Incompatible: debe esperar.

Protocolo de bloqueo en dos fases (2PL)

El Protocolo de Bloqueo en Dos Fases (2PL, Two-Phase Locking) es el mecanismo formal que garantiza que el uso de bloqueos produzca resultados equivalentes a ejecutar las transacciones una por una (serializabilidad). Divide la vida de una transacción en dos fases:

  • Fase de crecimiento (growing phase): la transacción solo puede adquirir bloqueos, nunca liberarlos.
  • Fase de decrecimiento (shrinking phase): la transacción solo puede liberar bloqueos, sin volver a solicitar ninguno nuevo.

En la práctica, la mayoría de los SMBDR usan una variante llamada 2PL estricto, donde todos los bloqueos se liberan hasta el COMMIT o ROLLBACK final, evitando que otras transacciones lean datos que después podrían deshacerse (lectura sucia).

El estándar SQL define además niveles de aislamiento, que equilibran consistencia contra rendimiento:

Tabla 6: Niveles de aislamiento (ANSI SQL)

NivelPermite lectura suciaPermite lectura no repetiblePermite lectura fantasma
READ UNCOMMITTEDSíSíSí
READ COMMITTEDNoSíSí
REPEATABLE READNoNoSí
SERIALIZABLENoNoNo

Cuando dos transacciones se bloquean mutuamente esperando un recurso que la otra tiene, ocurre un deadlock (interbloqueo). El SMBDR lo detecta construyendo un grafo de espera: si se forma un ciclo, hay deadlock, y el motor elige a una transacción como "víctima" para hacerle ROLLBACK y liberar el bloqueo.

Figura 2: Diagrama propio — grafo de espera: T1 espera un recurso que tiene T2 y T2 espera un recurso que tiene T1, formando un ciclo (deadlock).

Ejemplo

Cómo definir el nivel de aislamiento de una transacción:

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
START TRANSACTION;
SELECT stock FROM Productos WHERE id_producto = 5;
UPDATE Productos SET stock = stock - 1 WHERE id_producto = 5;
COMMIT;

Escenario de deadlock: la transacción T1 bloquea la fila A y después pide la fila B; al mismo tiempo, T2 bloquea la fila B y después pide la fila A. Ninguna puede avanzar: el SMBDR detecta el ciclo (Figura 2) y hace ROLLBACK a una de las dos.

2.4 Implementación de transacciones, procedimientos almacenados, disparadores, funciones y cursores

Definición

Además de agrupar operaciones en transacciones (START TRANSACTION … COMMIT, ver Unidad I, tema 1.5), un SMBDR permite crear objetos programables que viven y se ejecutan dentro del propio servidor: procedimientos almacenados, funciones, disparadores (triggers) y cursores.

Tabla 7: Procedimiento almacenado, función y disparador

Objeto¿Devuelve un valor?¿Cómo se invoca?
Procedimiento almacenadoOpcionalmente (parámetros de salida)Explícitamente, con CALL / EXEC.
FunciónSí, siempre un valorDentro de una expresión SQL, como SELECT funcion(x).
Disparador (trigger)NoAutomáticamente, ante un evento (INSERT, UPDATE, DELETE).

Un cursor es un puntero que permite recorrer, fila por fila, el resultado de una consulta dentro de un bloque procedural (algo que el SQL declarativo normal no hace por sí solo).

Ejemplo

-- Procedimiento almacenado con parámetros
DELIMITER //
CREATE PROCEDURE AumentarSalario(IN emp_id INT, IN porcentaje DECIMAL(5,2))
BEGIN
    UPDATE Empleados
    SET salario = salario * (1 + porcentaje / 100)
    WHERE id_empleado = emp_id;
END //
DELIMITER ;
CALL AumentarSalario(12, 5.0);

-- Función que devuelve un valor
CREATE FUNCTION AntiguedadAnios(fecha_ingreso DATE) RETURNS INT
DETERMINISTIC
RETURN TIMESTAMPDIFF(YEAR, fecha_ingreso, CURDATE());

-- Disparador: registra un historial cada vez que cambia un salario
CREATE TRIGGER trg_historial_salario
AFTER UPDATE ON Empleados
FOR EACH ROW
BEGIN
    IF OLD.salario <> NEW.salario THEN
        INSERT INTO HistorialSalarios (id_empleado, salario_anterior, salario_nuevo)
        VALUES (OLD.id_empleado, OLD.salario, NEW.salario);
    END IF;
END;

-- Cursor dentro de un procedimiento
DELIMITER //
CREATE PROCEDURE ListarEmpleadosActivos()
BEGIN
    DECLARE fin INT DEFAULT 0;
    DECLARE v_nombre VARCHAR(100);
    DECLARE cur CURSOR FOR SELECT nombre FROM Empleados WHERE activo = TRUE;
    DECLARE CONTINUE HANDLER FOR NOT FOUND SET fin = 1;

    OPEN cur;
    bucle: LOOP
        FETCH cur INTO v_nombre;
        IF fin = 1 THEN
            LEAVE bucle;
        END IF;
        SELECT v_nombre;
    END LOOP;
    CLOSE cur;
END //
DELIMITER ;

Manejo de excepciones

Un procedimiento almacenado robusto no debe asumir que todas sus instrucciones tendrán éxito: igual que un try/catch en un lenguaje de programación, SQL permite declarar manejadores de excepciones que capturan errores (por ejemplo, una violación de una restricción FOREIGN KEY) y deciden qué hacer en lugar de dejar la transacción a medias.

Ejemplo — Manejo de excepciones

-- MySQL: manejador declarado dentro del procedimiento
DELIMITER //
CREATE PROCEDURE RegistrarVentaSegura(IN p_producto INT, IN p_cantidad INT)
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SELECT 'Ocurrió un error, la venta no se registró' AS mensaje;
    END;

    START TRANSACTION;
    UPDATE Productos SET stock = stock - p_cantidad WHERE id_producto = p_producto;
    INSERT INTO Ventas (id_producto, cantidad) VALUES (p_producto, p_cantidad);
    COMMIT;
END //
DELIMITER ;

Si cualquier instrucción dentro del procedimiento falla (por ejemplo, p_producto no existe), el EXIT HANDLER intercepta el error, deshace lo hecho con ROLLBACK y regresa un mensaje, en vez de dejar el inventario descontado sin la venta correspondiente. En SQL Server, el mecanismo equivalente usa BEGIN TRY … END TRY / BEGIN CATCH … END CATCH.

2.5 Respaldos y recuperación de las Bases de Datos Relacionales

Definición

Un respaldo (backup) es una copia de la información de la base de datos que permite restaurarla ante una falla de hardware, software o un error humano. La recuperación (recovery) es el proceso de usar esos respaldos —junto con el registro de transacciones— para devolver la base de datos a un estado consistente.

Tabla 8: Tipos de respaldo

TipoQué respaldaVelocidad de restauración
CompletoToda la base de datos.Lenta de generar, rápida de restaurar por sí sola.
DiferencialTodo lo que cambió desde el último respaldo completo.Requiere el completo + el diferencial más reciente.
IncrementalSolo lo que cambió desde el último respaldo (completo o incremental).Requiere el completo + toda la cadena de incrementales.
De registro de transacciones (log)Las transacciones confirmadas desde el último respaldo de log.Permite recuperación a un punto exacto en el tiempo.

Figura 3: Diagrama propio — respaldo completo dominical, respaldos diferenciales el resto de la semana y respaldos de log cada hora.

Ejemplo

-- MySQL: respaldo completo desde la línea de comandos
mysqldump -u root -p Farmacia > respaldo_completo_domingo.sql

-- SQL Server: respaldo completo y diferencial
BACKUP DATABASE Farmacia TO DISK = 'D:\Respaldos\Farmacia_completo.bak';
BACKUP DATABASE Farmacia TO DISK = 'D:\Respaldos\Farmacia_dif_lunes.bak' WITH DIFFERENTIAL;

-- Para recuperar un martes, se restaura en este orden:
RESTORE DATABASE Farmacia FROM DISK = 'D:\Respaldos\Farmacia_completo.bak' WITH NORECOVERY;
RESTORE DATABASE Farmacia FROM DISK = 'D:\Respaldos\Farmacia_dif_lunes.bak' WITH RECOVERY;

Con la estrategia de la Figura 3, si el servidor falla el jueves a media tarde, se restaura el completo del domingo, luego el diferencial del miércoles (el más reciente) y, por último, los respaldos de log del jueves hasta el momento justo antes de la falla.

Actividad UTII_A6_RespaldoRecuperacion

Propósito

Practicar la generación de un respaldo y su posterior restauración (tema 2.5) como mecanismo de protección ante fallas.

Instrucciones

  1. Genera un respaldo completo de tu base de datos de empleados usando la herramienta de tu SMBDR (por ejemplo, mysqldump, pg_dump o el asistente gráfico correspondiente).
  2. Simula una falla: elimina o modifica accidentalmente una tabla completa con DROP TABLE o TRUNCATE.
  3. Restaura la base de datos a partir del respaldo generado en el paso 1 y verifica que los datos originales se recuperaron correctamente.

Evidencia que entregar

  1. Archivo de respaldo generado (.sql o el formato de tu SMBDR).
  2. Capturas de pantalla del proceso de respaldo y de restauración.
  3. Documento PDF con la corrida y una breve reflexión sobre la importancia de respaldar periódicamente.
