1.1 Funciones de SMBDR

La analogía del bibliotecario mágico

Haciendo una analogía, un SMBD es como un bibliotecario mágico muy veloz. Si la base de datos es un cuarto lleno de miles de libros sueltos, el SMBDR es el bibliotecario que sabe exactamente en qué estante está cada página, quién tiene permiso de leerla y toma notas si alguien cambia una palabra.

Por lo anterior nos damos cuenta de la importancia de los SMBDR, por eso antes de continuar es necesario conocer qué es un sistema manejador de bases de datos relacional (SMBDR).

¿Qué es un SMBDR?

Es un conjunto de programas, subrutinas o procedimientos que nos van a permitir gestionar (administrar) una base de datos. Un SMBDR es un software que sirve para estructurar, almacenar, manipular, ordenar, proteger y buscar la información de forma rápida y segura. Sirve como un intermediario entre las personas y los datos guardados en una computadora.

Un SMBDR tiene tres funciones principales

  • Definición o descripción
  • Manipulación
  • Control

Definición o descripción (el plano)

Para cumplir con esta función, es necesario utilizar el Lenguaje de Definición de Datos (DDL) del lenguaje SQL (Lenguaje Estructurado de Consulta). Se le dice el plano porque sirve para diseñar dónde se va a guardar la información. Es como decidir cuántas columnas y filas va a tener una tabla, por ejemplo Boleta, Nombre_Alumno, Edad_Alumno y Teléfono.

Las instrucciones del DDL sirven para crear con CREATE, modificar con ALTER o eliminar con DROP objetos como estos

  • Tablas
  • Vistas
  • Índices
  • Procedimientos
  • Triggers
  • Transacciones

Manipulación

Para cumplir con esta función, es necesario utilizar el Lenguaje de Manipulación de Datos (DML) del lenguaje SQL (Lenguaje Estructurado de Consulta). El DML es un conjunto de instrucciones (comandos) que sirven para modificar el estado de los datos que residen en las tablas (registros o filas), respetando las restricciones de integridad. Permite a los usuarios hacer cambios en los datos reales.

Cualquiera de estas instrucciones sirve para uno o varios registros de la tabla

  • INSERT para agregar nuevos registros.
  • DELETE para borrar registros.
  • UPDATE para modificar valores de los registros.
  • SELECT para efectuar cualquier consulta.

Control (el Guardián)

Para cumplir con esta función, es necesario utilizar el Lenguaje de Control de Datos (DCL) del lenguaje SQL (lenguaje estructurado de consulta). Asegura que nadie robe la información ni la borre por error. Controla que dos personas no cambien el mismo dato al mismo tiempo (concurrencia) y crea copias de seguridad por si la computadora se apaga de repente.

Las instrucciones del DCL sirven para dar o quitar estos permisos

  • GRANT — autoriza un privilegio sobre un objeto.
  • REVOKE — retira un privilegio ya autorizado.

Permisos que se les pueden dar a los usuarios sobre tablas y vistas

  • INSERT para agregar nuevos registros.
  • DELETE para borrar registros.
  • UPDATE para modificar valores de los registros.
  • SELECT para efectuar cualquier consulta.
  • INDEX para accesar de forma directa y rápida.
  • ALTER para modificar campos de una tabla.

Ejemplo

Imagínate que en la escuela te toca armar, desde cero, la lista de calificaciones de un grupo. Las tres funciones del SMBDR van saliendo una tras otra

  • Primero el plano (DDL). Antes de escribir un solo nombre, decides qué columnas lleva la lista, o sea Boleta, Nombre_Alumno, Grupo y Promedio. Eso es un CREATE TABLE, apenas estás dibujando el molde y todavía va vacío.
  • Luego el trabajo diario (DML). Ya con el molde listo, das de alta a cada alumno con INSERT, corriges con UPDATE el nombre que quedó mal escrito y, si alguien se dio de baja, lo quitas con DELETE. Cuando el maestro pide "pásame los promedios de todo el grupo de un jalón", eso es un SELECT.
  • Al final, el guardián (DCL). Al prefecto le das permiso de SELECT para que pueda consultar, pero no de DELETE, para que no borre nada por accidente, y eso se hace con GRANT. Y si dos maestros intentan cambiar la misma calificación al mismo tiempo, el SMBDR los forma, deja pasar a uno y hace esperar al otro para que el dato no se revuelva.

1.2 Modelo relacional y las 12 reglas de Codd

La analogía del archivero de listas de la escuela

Piensa en el modelo relacional como un archivero de la escuela lleno de listas. Cada lista es una tabla, cada renglón es un alumno y cada columna es un dato de ese alumno (boleta, nombre, grupo, etc.). Lo bonito es que una lista se puede "amarrar" con otra. La lista de calificaciones se conecta con la de alumnos usando la boleta, y así no tienes que volver a escribir el nombre en todos lados.

Esta forma de acomodar los datos la propuso Edgar Frank Codd, un investigador de IBM, en 1970. Antes de él, la información se guardaba de formas muy difíciles de mantener. Codd propuso que todo se podía acomodar con tablas y matemáticas sencillas, y esa idea terminó siendo la base de casi todos los SMBDR de hoy.

Antes de ver las reglas vale la pena aclarar algunas palabras del modelo relacional

Tabla 1 — Palabras básicas del modelo relacional

Término¿Qué es?Ejemplo

TuplaFila o registro de la relación.Un alumno en particular
AtributoColumna o campo de la relación.nombre, correo
DominioConjunto de valores válidos que puede tomar un atributo.Enteros positivos para edad

Para que un sistema se pueda llamar de verdad relacional, Codd escribió trece reglas, de la 0 a la 12

Tabla 2 — Las trece reglas de Codd

ReglaNombreDescripción
0Regla fundamentalEl sistema debe poder gestionar la base de datos completamente a través de sus capacidades relacionales.
1De la informaciónToda la información se representa explícitamente en forma de valores dentro de tablas.
2Acceso garantizadoCada valor debe ser accesible mediante el nombre de la tabla, el valor de su clave primaria y el nombre de la columna.
3Tratamiento sistemático de nulosEl sistema debe soportar valores nulos (información desconocida o no aplicable) de manera uniforme.
4Catálogo dinámico en líneaLos metadatos (catálogo) se describen con el mismo modelo relacional y se consultan con el mismo lenguaje.
5Sublenguaje de datos comprensivoDebe existir un único lenguaje (por ejemplo, SQL) para definir datos, manipularlos, controlar la integridad y las transacciones.
6Actualización de vistasToda vista que sea teóricamente actualizable debe poder actualizarse a través del sistema.
7Inserción, actualización y eliminación de alto nivelEstas operaciones deben poder aplicarse a conjuntos completos de tuplas, no solo fila por fila.
8Independencia físicaLos cambios en el almacenamiento físico no deben afectar a las aplicaciones.
9Independencia lógicaLos cambios en la estructura lógica que preserven la información no deben afectar a las aplicaciones.
10Independencia de integridadLas reglas de integridad se definen en el lenguaje relacional y se almacenan en el catálogo, no dentro de los programas.
11Independencia de distribuciónEl lenguaje relacional debe funcionar igual aunque los datos estén distribuidos en varios servidores.
12De no subversiónSi el sistema ofrece un lenguaje de bajo nivel (registro por registro), este no debe poder saltarse las reglas de integridad del lenguaje relacional.

Ejemplo

La tabla Alumnos (matricula, nombre, id_carrera) ilustra la Regla 1, porque toda la información está representada como valores dentro de una tabla. Además, el valor "Juárez López María" es accesible sin ambigüedad indicando la tabla Alumnos, la clave matricula = 2024630123 y la columna nombre, lo que ilustra la Regla 2 (acceso garantizado).

Ejercicio — Verdadero o falso (clic para desplegar)

Un desarrollador guarda parte de la información de sus clientes en la propia base de datos y otra parte en un archivo de texto plano fuera del motor, al que accede con código a la medida. Esto incumple la Regla 1 (de la información), porque no toda la información está representada dentro de tablas del SMBDR. A partir de ese caso, di si cada afirmación es verdadera o falsa

1. La Regla 12 (de no subversión) permite que un lenguaje de bajo nivel evada las restricciones de integridad definidas en SQL.

2. Si una vista puede actualizarse teóricamente, el sistema debe permitir actualizarla — esto corresponde a la Regla 6.

3. Que cambiar la forma en que se almacenan físicamente los archivos en disco no afecte a las aplicaciones es la independencia lógica (Regla 9).

4. La Regla 4 exige que el catálogo del sistema se consulte con un lenguaje distinto al usado para los datos del usuario.

1.3 Componentes y ambiente de trabajo

La analogía del taller mecánico

Imagínate que un SMBDR es como un taller mecánico. Ahí hay herramientas (el software), refacciones y autos (los datos), mecánicos con distintos oficios (los usuarios) y un manual de procedimientos pegado en la pared (las reglas de cómo se usa y se respalda todo). Si falta cualquiera de esas partes, el taller no jala.

En la práctica, ese taller casi siempre trabaja en modo cliente y servidor. Las aplicaciones, que son los clientes, mandan sus pedidos en SQL por la red y un solo encargado, que es el servidor, atiende a todos uno por uno, para que nadie se estorbe ni se pierda un dato.

Por dentro, el servidor del SMBDR se arma con varias partes que trabajan juntas

  • Procesador de consultas. Revisa y traduce el SQL que llega, y una parte llamada optimizador escoge la forma más rápida de resolverlo.
  • Gestor de transacciones. Se asegura de que cada grupo de operaciones se haga completo o no se haga, y organiza los candados cuando varios usuarios trabajan a la vez. A esas garantías se les llama ACID.
  • Gestor de almacenamiento. Junta la memoria rápida donde se dejan los datos que más se usan y la parte que lee y escribe en el disco.
  • Catálogo del sistema. Es la libreta donde el SMBDR anota qué tablas, columnas, índices, usuarios y permisos existen. También se le dice diccionario de datos.

Figura 1. Diagrama propio. El modo cliente y servidor y las partes de adentro de un SMBDR.

Ejemplo

En una tienda en línea, el navegador del comprador (cliente) envía una petición al servidor de aplicaciones, este construye una consulta SQL como SELECT * FROM Productos WHERE categoria = 'Zapatos' y la envía al servidor de base de datos (MySQL, PostgreSQL, SQL Server, etc.). Ahí, el procesador de consultas la analiza y optimiza, el gestor de almacenamiento localiza las páginas en disco o en el buffer, y el resultado regresa al cliente.

1.4 Estructura de almacenamiento y objetos

La analogía del edificio de archivo

Una base de datos es como un edificio de archivo. El edificio completo es la base de datos. Cada piso es un esquema, que es un cajón grande con nombre donde se juntan cosas relacionadas, casi siempre de un mismo usuario. Y en cada piso hay archiveros, cajones y etiquetas, que son los objetos como tablas, vistas e índices. Abajo hay un sótano con la maquinaria, que son los archivos guardados en el disco y que el usuario normal nunca ve.

Así, un mismo objeto tiene dos caras. La parte lógica es lo que tú manejas con SQL, como la tabla y sus columnas. La parte física es cómo se guarda de verdad en el disco. El SMBDR se encarga de que puedas cambiar una sin romper la otra.

Estos son los objetos que el usuario maneja directamente con SQL

Tabla 3 — Objetos que se pueden manejar en un SMBDR

Índices clusterizados y no clusterizados

Un índice clusterizado decide el orden real en que se guardan las filas de la tabla en el disco. Por eso solo puede haber uno por tabla, casi siempre sobre la llave primaria. Un índice no clusterizado es una lista aparte que apunta a las filas sin moverlas de lugar, así que una tabla puede tener varios. Si no dices otra cosa, un CREATE INDEX como el de abajo crea uno no clusterizado.

Ejemplo

Crear una tabla, un índice y una vista para un catálogo de libros

CREATE TABLE Libros (
    id_libro     INT PRIMARY KEY AUTO_INCREMENT,
    titulo       VARCHAR(120) NOT NULL,
    autor        VARCHAR(80)  NOT NULL,
    anio         INT,
    disponible   BOOLEAN DEFAULT TRUE
);

-- Índice para acelerar búsquedas por autor
CREATE INDEX idx_autor ON Libros(autor);

-- Vista con solo los libros disponibles
CREATE VIEW VistaLibrosDisponibles AS
SELECT id_libro, titulo, autor
FROM Libros
WHERE disponible = TRUE;

1.5 Instrucciones estándar de lenguaje estructurado de consulta (SQL)

La analogía del idioma para hablarle al bibliotecario

Si el SMBDR es el bibliotecario mágico del tema 1.1, SQL es el idioma con el que le hablas. En lugar de ir tú a buscar entre los estantes, solo le dices qué quieres y él ve cómo conseguirlo. Es un idioma parejo, casi todos los manejadores lo entienden, con pequeñas diferencias de acento.

Ese idioma tiene cuatro tonos, según lo que le pidas. Armar o cambiar los muebles de la biblioteca es DDL. Mover libros de aquí para allá es DML. Decir quién tiene llave de qué sala es DCL. Y cerrar bien un trámite completo para que no quede a medias es TCL.

Tabla 5 — Las cuatro partes del SQL

SublenguajeNombreInstrucciones principales

DMLData Manipulation LanguageSELECT, INSERT, UPDATE, DELETE
DCLData Control LanguageGRANT, REVOKE
TCLTransaction Control LanguageCOMMIT, ROLLBACK, SAVEPOINT

Caso práctico integral de la Farmacia "San Rafael"

La farmacia "San Rafael" quiere pasar a la computadora el control de sus productos y sus ventas. Aquí se ve el mismo caso con las cuatro partes de SQL, en el orden en que se usarían en un proyecto de verdad. Primero se arma la estructura con DDL. Después se cargan y mueven los datos con DML. Luego se controla quién puede hacer qué con DCL. Y al final se protege la operación más delicada del negocio, que es la venta, juntándola en una transacción con TCL.

PASO 1 · DDL Definición de la estructura

Lo primero es crear las tablas del inventario y de las ventas. Ventas se conecta con Productos por una llave foránea, así no se puede vender un producto que no esté en el catálogo

CREATE TABLE Productos (
    id_producto  INT PRIMARY KEY AUTO_INCREMENT,
    nombre       VARCHAR(100) NOT NULL,
    precio       DECIMAL(8,2) NOT NULL,
    stock        INT NOT NULL DEFAULT 0
);

CREATE TABLE Ventas (
    id_venta     INT PRIMARY KEY AUTO_INCREMENT,
    id_producto  INT NOT NULL,
    cantidad     INT NOT NULL,
    total        DECIMAL(8,2) NOT NULL,
    fecha        DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (id_producto) REFERENCES Productos(id_producto)
);

Un mes después, la farmacia quiere avisos cuando un medicamento esté por acabarse, así que hay que cambiar la estructura sin perder lo que ya está guardado. Para eso se usa ALTER TABLE

ALTER TABLE Productos ADD stock_minimo INT DEFAULT 5;

Si más adelante se quisiera vaciar la tabla de ventas de una etapa de pruebas sin borrar la tabla ni tocar Productos, se usaría TRUNCATE. Y si un módulo completo dejara de usarse, se quita con DROP

TRUNCATE TABLE Ventas;      -- vacía la tabla, conserva su estructura
DROP TABLE Ventas;          -- elimina la tabla por completo, con todo y estructura

INSERT INTO Productos (nombre, precio, stock, stock_minimo) VALUES

    ('Ibuprofeno 400mg',  48.50,  80, 15),

PASO 3 · DCL Control de acceso

No todos los empleados llevan los mismos permisos. El cajero solo necesita ver precios y existencias y anotar ventas, pero nunca debería poder borrar productos ni cambiar la estructura de las tablas. A eso de dar solo lo necesario se le llama mínimo privilegio

GRANT SELECT ON Productos TO 'cajero'@'localhost';
GRANT SELECT, INSERT ON Ventas TO 'cajero'@'localhost';

Si tiempo después se ve que el usuario cajero se quedó con un permiso que ya no debería tener, por ejemplo el de borrar ventas, ese permiso se quita con REVOKE sin tocar los demás

REVOKE DELETE ON Ventas FROM 'cajero'@'localhost';
PASO 4 · TCL La venta como transacción segura

Anotar una venta en realidad son dos pasos que tienen que pasar juntos, bajar el stock y meter el registro de la venta. Si el sistema fallara justo entre esos dos pasos, por ejemplo si se corta la conexión, el inventario quedaría descontado sin que exista la venta, y eso es un problema serio. Por eso los dos pasos se juntan en una sola transacción

START TRANSACTION;

UPDATE Productos SET stock = stock - 1 WHERE id_producto = 1;

SAVEPOINT stock_descontado;   -- punto de control intermedio

INSERT INTO Ventas (id_producto, cantidad, total)
VALUES (1, 1, 35.00);

-- Si algo saliera mal después de descontar el stock, podríamos
-- deshacer solo hasta el punto de control:
-- ROLLBACK TO stock_descontado;

COMMIT;   -- confirma ambas operaciones de forma permanente y atómica

Actividad UTI_A3_Biblioteca_DDL

Propósito

Utilizar sentencias DDL (temas 1.4 y 1.5) para declarar la estructura completa de una base de datos relacional a partir de un caso propuesto, incluyendo llaves primarias y foráneas.

Instrucciones

  1. Diseña una base de datos llamada Biblioteca con al menos 3 tablas relacionadas entre sí (por ejemplo Autores, Libros y Prestamos), definiendo tipos de datos apropiados para cada columna.
  2. Escribe el script SQL con las instrucciones CREATE DATABASE y CREATE TABLE necesarias, incluyendo PRIMARY KEY y las FOREIGN KEY que relacionen las tablas.
  3. Ejecuta el script en tu SMBDR y verifica con DESCRIBE (o su equivalente) que las tablas se crearon con la estructura esperada.

Actividad UTI_A4_DML_DCL_TCL

Propósito

Practicar las instrucciones DML, DCL y TCL (tema 1.5) sobre la base de datos Biblioteca creada en la actividad anterior, reforzando el manejo de transacciones y de permisos.

Instrucciones

  1. Sobre la base de datos Biblioteca, inserta al menos 5 registros en cada tabla usando INSERT INTO.
