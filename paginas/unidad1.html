1.1 Funciones de SMBDR

Definición

Un Sistema Manejador (o Gestor) de Bases de Datos Relacionales (SMBDR), del inglés RDBMS, es el software que permite crear, definir, mantener y controlar el acceso a una base de datos organizada bajo el modelo relacional. Actúa como intermediario entre los usuarios/aplicaciones y los archivos físicos donde se almacena la información, ocultando la complejidad del almacenamiento y garantizando que los datos se manipulen de forma correcta, segura y consistente.

Para cumplir ese papel, todo SMBDR debe ofrecer un conjunto de funciones básicas:

  • Definición de datos: permite describir la estructura de la base de datos (tablas, columnas, tipos de dato y relaciones) mediante un lenguaje de definición de datos (DDL).
  • Manipulación de datos: permite insertar, consultar, actualizar y eliminar información mediante un lenguaje de manipulación de datos (DML).
  • Independencia de los datos: separa la forma en que los datos se almacenan físicamente de la forma en que los ve el usuario, de modo que los cambios en el almacenamiento no afecten a las aplicaciones.
  • Control de redundancia: evita, en la medida de lo posible, que la misma información se duplique innecesariamente en distintos lugares.
  • Integridad de los datos: aplica reglas y restricciones (claves primarias, claves foráneas, valores obligatorios, etc.) para que la información sea correcta y coherente.
  • Seguridad y control de acceso: autentica usuarios y autoriza qué acciones puede realizar cada uno sobre qué objetos.
  • Control de concurrencia: coordina que varios usuarios trabajen al mismo tiempo sobre la misma información sin que se generen inconsistencias.
  • Respaldo y recuperación: permite generar copias de seguridad y restaurar la base de datos ante fallas de hardware, software o errores humanos.
  • Diccionario de datos o catálogo: mantiene los metadatos (información sobre la propia base de datos: tablas, columnas, usuarios, permisos, etc.).

Ejemplo

En el sistema de control escolar de una universidad, un SMBDR como MySQL o PostgreSQL:

  • Impide registrar dos veces al mismo alumno con la misma boleta (integridad).
  • Permite que la coordinación consulte calificaciones mientras control escolar da de alta nuevas inscripciones, sin que un proceso bloquee al otro (concurrencia).
  • Restringe que solo el personal autorizado pueda modificar las calificaciones ya publicadas (seguridad).
  • Genera un respaldo automático cada noche por si el servidor falla (respaldo y recuperación).

1.2 Modelo relacional y las 12 reglas de Codd

Definición

El modelo relacional fue propuesto por Edgar F. Codd en 1970 mientras trabajaba en IBM. Representa la información como un conjunto de relaciones (tablas), basándose en la teoría de conjuntos y la lógica de predicados. Su objetivo fue independizar la forma en que se organizan los datos de la forma en que se almacenan físicamente.

Antes de ver las reglas, conviene precisar el vocabulario del modelo relacional:

Tabla 1: Vocabulario básico del modelo relacional

TérminoDefiniciónEjemplo
RelaciónTabla que almacena datos de una misma entidad.Tabla Alumnos
TuplaFila o registro de la relación.Un alumno en particular
AtributoColumna o campo de la relación.nombre, correo
DominioConjunto de valores válidos que puede tomar un atributo.Enteros positivos para edad
Clave primaria (PK)Atributo (o conjunto de atributos) que identifica de forma única cada tupla.matricula
Clave foránea (FK)Atributo que referencia la clave primaria de otra relación, estableciendo un vínculo entre tablas.id_carrera en Alumnos

Para que un sistema pueda considerarse verdaderamente relacional, Codd definió trece reglas, numeradas del 0 al 12:

Tabla 2: Las trece reglas de Codd para sistemas relacionales

ReglaNombreDescripción
0Regla fundamentalEl sistema debe poder gestionar la base de datos completamente a través de sus capacidades relacionales.
1De la informaciónToda la información se representa explícitamente en forma de valores dentro de tablas.
2Acceso garantizadoCada valor debe ser accesible mediante el nombre de la tabla, el valor de su clave primaria y el nombre de la columna.
3Tratamiento sistemático de nulosEl sistema debe soportar valores nulos (información desconocida o no aplicable) de manera uniforme.
4Catálogo dinámico en líneaLos metadatos (catálogo) se describen con el mismo modelo relacional y se consultan con el mismo lenguaje.
5Sublenguaje de datos comprensivoDebe existir un único lenguaje (por ejemplo, SQL) para definir datos, manipularlos, controlar la integridad y las transacciones.
6Actualización de vistasToda vista que sea teóricamente actualizable debe poder actualizarse a través del sistema.
7Inserción, actualización y eliminación de alto nivelEstas operaciones deben poder aplicarse a conjuntos completos de tuplas, no solo fila por fila.
8Independencia físicaLos cambios en el almacenamiento físico no deben afectar a las aplicaciones.
9Independencia lógicaLos cambios en la estructura lógica que preserven la información no deben afectar a las aplicaciones.
10Independencia de integridadLas reglas de integridad se definen en el lenguaje relacional y se almacenan en el catálogo, no dentro de los programas.
11Independencia de distribuciónEl lenguaje relacional debe funcionar igual aunque los datos estén distribuidos en varios servidores.
12De no subversiónSi el sistema ofrece un lenguaje de bajo nivel (registro por registro), este no debe poder saltarse las reglas de integridad del lenguaje relacional.

Ejemplo

La tabla Alumnos (matricula, nombre, id_carrera) ilustra la Regla 1, porque toda la información está representada como valores dentro de una tabla. Además, el valor "Juárez López María" es accesible sin ambigüedad indicando la tabla Alumnos, la clave matricula = 2024630123 y la columna nombre, lo que ilustra la Regla 2 (acceso garantizado).

Ejercicio — Verdadero o falso (clic para desplegar)

Un desarrollador guarda parte de la información de sus clientes en la propia base de datos y otra parte en un archivo de texto plano fuera del motor, al que accede con código a la medida. Esto incumple la Regla 1 (de la información), porque no toda la información está representada dentro de tablas del SMBDR. A partir de ese caso, evalúa las siguientes afirmaciones:

1. La Regla 12 (de no subversión) permite que un lenguaje de bajo nivel evada las restricciones de integridad definidas en SQL.

2. Si una vista puede actualizarse teóricamente, el sistema debe permitir actualizarla — esto corresponde a la Regla 6.

3. Que cambiar la forma en que se almacenan físicamente los archivos en disco no afecte a las aplicaciones es la independencia lógica (Regla 9).

4. La Regla 4 exige que el catálogo del sistema se consulte con un lenguaje distinto al usado para los datos del usuario.

1.3 Componentes y ambiente de trabajo

Definición

El ambiente de trabajo de un SMBDR suele basarse en una arquitectura Cliente/Servidor: las aplicaciones (clientes) envían solicitudes en SQL a través de la red, y un proceso servidor centraliza el acceso a la base de datos, coordinando a todos los usuarios de forma segura y consistente.

Internamente, el servidor del SMBDR se organiza en varios componentes que colaboran entre sí:

  • Procesador de consultas: analiza (parser) y traduce el SQL recibido, y el optimizador elige el plan de ejecución más eficiente.
  • Gestor de transacciones: garantiza las propiedades ACID (Atomicidad, Consistencia, Aislamiento y Durabilidad) y coordina los bloqueos entre usuarios concurrentes.
  • Gestor de almacenamiento: incluye al administrador de buffers (memoria caché de páginas de datos) y al administrador de archivos, encargados de leer y escribir en disco.
  • Catálogo del sistema (diccionario de datos): repositorio de metadatos: tablas, columnas, índices, usuarios y permisos existentes.

Figura 1: Diagrama propio — arquitectura cliente/servidor y componentes internos de un SMBDR.

Ejemplo

En una tienda en línea, el navegador del comprador (cliente) envía una petición al servidor de aplicaciones, este construye una consulta SQL como SELECT * FROM Productos WHERE categoria = 'Zapatos' y la envía al servidor de base de datos (MySQL, PostgreSQL, SQL Server, etc.). Ahí, el procesador de consultas la analiza y optimiza, el gestor de almacenamiento localiza las páginas en disco o en el buffer, y el resultado regresa al cliente.

1.4 Estructura de almacenamiento y objetos

Definición

Un SMBDR ya implementado distingue, en su arquitectura interna, entre el lógico, formado por los objetos que el usuario manipula con SQL (tablas, vistas, índices, etc.), y el físico, formado por la manera en que esos objetos realmente se guardan en el disco (archivos, extensiones y bloques). El SMBDR mantiene la independencia entre ambos niveles (regla 8 y 9 de Codd). Nota: esta distinción es distinta de los tres niveles de diseño (conceptual/lógico/físico) que se explicaron al inicio de la unidad (ver Tabla 0): aquí "lógico" y "físico" describen dos caras de un mismo objeto ya implementado, no dos fases del proceso de diseño.

Los objetos que el usuario administra directamente con SQL son:

Tabla 3: Objetos administrables de un SMBDR

ObjetoDescripción
TablaEstructura compuesta por filas y columnas donde se almacenan los datos de una entidad.
VistaConsulta almacenada que se comporta como una tabla virtual, sin duplicar los datos.
ÍndiceEstructura auxiliar (comúnmente un árbol B+) que acelera la búsqueda de filas. Un índice clusterizado tiene además un componente físico: determina el orden real en que se guardan las filas en disco (ver más abajo).
Procedimiento almacenadoBloque de código SQL/procedural que se guarda y ejecuta en el servidor.
Disparador (trigger)Bloque de código que se ejecuta automáticamente ante un evento (INSERT, UPDATE, DELETE).
SecuenciaGenerador de valores numéricos consecutivos, útil para claves autoincrementales.

Índices clusterizados y no clusterizados

Un índice clusterizado (clustered) determina el orden físico en que se almacenan las filas de la tabla en disco; por eso solo puede haber uno por tabla (normalmente sobre la clave primaria). Un índice no clusterizado (non-clustered) es una estructura aparte que apunta a las filas sin reordenarlas físicamente, así que una tabla puede tener varios. Salvo que se indique lo contrario, un CREATE INDEX como el de abajo crea un índice no clusterizado.

Ejemplo

Creación de una tabla, un índice y una vista para un catálogo de libros:

CREATE TABLE Libros (
    id_libro     INT PRIMARY KEY AUTO_INCREMENT,
    titulo       VARCHAR(120) NOT NULL,
    autor        VARCHAR(80)  NOT NULL,
    anio         INT,
    disponible   BOOLEAN DEFAULT TRUE
);

-- Índice para acelerar búsquedas por autor
CREATE INDEX idx_autor ON Libros(autor);

-- Vista con solo los libros disponibles
CREATE VIEW VistaLibrosDisponibles AS
SELECT id_libro, titulo, autor
FROM Libros
WHERE disponible = TRUE;

1.5 Instrucciones estándar de lenguaje estructurado de consulta (SQL)

Definición

SQL (Structured Query Language) es el lenguaje estándar (ANSI/ISO) declarativo para definir, manipular y controlar la información de un SMBDR: el usuario indica qué datos necesita, y es el optimizador del motor quien decide cómo obtenerlos. Se divide en cuatro sublenguajes según la acción que se desea realizar.

Tabla 5: Sublenguajes del SQL

SublenguajeNombreInstrucciones principales
DDLData Definition LanguageCREATE, ALTER, DROP, TRUNCATE
DMLData Manipulation LanguageSELECT, INSERT, UPDATE, DELETE
DCLData Control LanguageGRANT, REVOKE
TCLTransaction Control LanguageCOMMIT, ROLLBACK, SAVEPOINT

Caso práctico integral: Farmacia "San Rafael"

La farmacia "San Rafael" quiere digitalizar el control de sus productos y sus ventas. A continuación se desarrolla el mismo caso a través de los cuatro sublenguajes de SQL, en el orden natural en que se usarían en un proyecto real: primero se define la estructura (DDL), después se carga y manipula la información (DML), luego se controla quién puede hacer qué (DCL) y, finalmente, se protege la operación más delicada del negocio — la venta — como una transacción (TCL).

PASO 1 · DDL Definición de la estructura

Lo primero es crear las tablas que representarán el inventario y las ventas. Ventas se relaciona con Productos mediante una clave foránea, de modo que no se pueda vender un producto que no exista en el catálogo:

CREATE TABLE Productos (
    id_producto  INT PRIMARY KEY AUTO_INCREMENT,
    nombre       VARCHAR(100) NOT NULL,
    precio       DECIMAL(8,2) NOT NULL,
    stock        INT NOT NULL DEFAULT 0
);

CREATE TABLE Ventas (
    id_venta     INT PRIMARY KEY AUTO_INCREMENT,
    id_producto  INT NOT NULL,
    cantidad     INT NOT NULL,
    total        DECIMAL(8,2) NOT NULL,
    fecha        DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (id_producto) REFERENCES Productos(id_producto)
);

Un mes después, la farmacia decide generar alertas cuando un medicamento esté por agotarse, así que la estructura debe evolucionar sin perder los datos ya existentes; para eso se usa ALTER TABLE:

ALTER TABLE Productos ADD stock_minimo INT DEFAULT 5;

Si más adelante se quisiera vaciar la tabla de ventas de un periodo de pruebas (sin perder la estructura ni afectar a Productos), se usaría TRUNCATE; y si un módulo completo dejara de utilizarse, se retiraría con DROP:

TRUNCATE TABLE Ventas;      -- vacía la tabla, conserva su estructura
DROP TABLE Ventas;          -- elimina la tabla por completo, con todo y estructura

PASO 3 · DCL Control de acceso

No todos los empleados deben tener los mismos permisos: el cajero solo necesita consultar precios/existencias y registrar ventas, pero jamás debería poder borrar productos ni modificar la estructura de las tablas (principio de mínimo privilegio):

GRANT SELECT ON Productos TO 'cajero'@'localhost';
GRANT SELECT, INSERT ON Ventas TO 'cajero'@'localhost';

Si tiempo después se detecta que el usuario cajero conserva un permiso que ya no debería tener (por ejemplo, para borrar ventas), ese privilegio se retira con REVOKE sin afectar los demás permisos ya otorgados:

REVOKE DELETE ON Ventas FROM 'cajero'@'localhost';
PASO 4 · TCL La venta como transacción segura

Registrar una venta en realidad implica dos operaciones que deben ocurrir juntas: descontar el stock e insertar el registro de venta. Si el sistema fallara justo entre esas dos instrucciones (por ejemplo, se corta la conexión), el inventario quedaría descontado sin que exista la venta correspondiente — una inconsistencia grave. Por eso ambas operaciones se agrupan en una sola transacción:

START TRANSACTION;

UPDATE Productos SET stock = stock - 1 WHERE id_producto = 1;

SAVEPOINT stock_descontado;   -- punto de control intermedio

INSERT INTO Ventas (id_producto, cantidad, total)
VALUES (1, 1, 35.00);

-- Si algo saliera mal después de descontar el stock, podríamos
-- deshacer solo hasta el punto de control:
-- ROLLBACK TO stock_descontado;

COMMIT;   -- confirma ambas operaciones de forma permanente y atómica
